# The sample dataset

`fixtures/` holds a **fully synthetic intrusion training scenario** and the pipeline output
it produces. It is what `npm test` runs against, what the quickstart in the README
distills, and what a conformance failure is measured by.

There is a **second** estate here too — [`sample-estate/`](#sample-estate--a-second-estate-to-practice-on),
at the bottom of this file. Nothing pins it, which is the point: it is the folder to
experiment on.

**Nothing here was captured from a real network.** Every host, user, IP address, domain,
process, hash and certificate was invented for the scenario. The organization is
fictional. The files are generated by a renderer and verified against the pipeline they
feed, not exported from a production estate.

## The scenario

3,859 events over eight hours on 2026-03-09, across 26 hosts in the fictional `LARKSPUR`
domain, in four log dialects.

One workstation is compromised. Three process-create events on `DEVBOX-07` (10.20.30.41)
carry the whole chain:

1. `14:00:13` — `explorer.exe` spawns `powershell.exe`, with a command line naming
   `WINWORD.EXE "invoice.docm"`.
2. `14:00:15` — `node.exe` spawns `powershell.exe` with `-NoProfile -WindowStyle Hidden
   -EncodedCommand <base64>`. Decoded as UTF-16LE, that command downloads a payload from
   193.42.33.81, writes it to `%LOCALAPPDATA%\npm-cache\_tmp\node-bridge.exe`, and starts
   it.
3. `14:00:23` — `powershell.exe` spawns exactly that binary.

`node-bridge.exe` then beacons to 193.42.33.81 on port 443, over TLS with a self-signed
certificate and no SNI, and sends out far more than it receives.

Everything else on the estate is ordinary: 25 hosts running browsers, Outlook, OneDrive,
an EDR sensor, a backup agent, VS Code. They generate normal traffic — and some of it
scores high, which is the point.

### The ten candidates

Running `athanor fixtures/raw` produces exactly these, in this order:

| Id | Score | What it is |
| --- | --- | --- |
| `BCN-001` | 0.9395 | `bastion-sensor.exe` → 104.18.22.51. The **highest-scoring beacon is the EDR agent** — a perfectly regular, perfectly consistent check-in. Benign. |
| `BCN-002` | 0.8560 | `node-bridge.exe` → 193.42.33.81. The actual implant. |
| `BCN-003` | 0.7695 | `svchost.exe` on a second host → 91.213.50.77. Ambiguous by construction. |
| `BCN-004` | 0.7023 | `AzureBackupAgent.exe` → a cloud endpoint. Benign. |
| `BCN-005` | 0.6996 | `OUTLOOK.EXE` → a mail endpoint. Benign. |
| `DT-001` | 0.9989 | The same `node-bridge.exe` connection, seen as outbound volume. |
| `TLS-001` | 0.5000 | The same connection again, seen as a certificate anomaly. |
| `UPCA-001` | 0.8500 | `node.exe` → `powershell.exe` on `DEVBOX-07`. |
| `UPCA-002` | 0.8500 | `powershell.exe` → `node-bridge.exe` on `DEVBOX-07`. |
| `PSI-001` | 0.9000 | The `-EncodedCommand` invocation itself. |

Three properties of that list are deliberate teaching material:

- **The top-ranked beacon is benign.** Score order is not suspicion order, and a dataset
  where the highest score is always the intrusion teaches the wrong reflex.
- **`BCN-002`, `DT-001` and `TLS-001` are one connection seen three ways.** Nothing in
  athanor composes them; five scorers run independently and each reports what it saw.
- **`TLS-001` has `attribution.confidence: "unavailable"`** with
  `[no_eid3_match, partial_evidence_unattributed]`. The Zeek `ssl.log` connection ids do
  not join to any `conn.log` record, so the bridge to a process has no first span. That is
  a real join failure, reproduced on purpose.

Three more candidates score 0.5 and fall below the PowerShell floor of 0.6. They are in
the caput mortuum, and `--discards` writes them out.

## The files

### `raw/` — the four dialect files

The input to the raw-ingest pin, and the folder the quickstart distills. These are the
shapes a collector emits: no event ids, native field names, per-dialect timestamp formats.

| File | Records | Dialect |
| --- | --- | --- |
| `conn.log` | 1,614 | Zeek `conn.log`, JSON lines |
| `ssl.log` | 480 | Zeek `ssl.log` pre-joined with `x509.log`, JSON lines |
| `sysmon-eid1.jsonl` | 151 | Sysmon EID 1 `process_create`, flat JSONL |
| `sysmon-eid3.jsonl` | 1,614 | Sysmon EID 3 `network_connect`, flat JSONL |

**`raw/` must stay exactly these four files.** `ingestFolder` reads every file in the
folder it is given, so a fifth one would insert events into the merge and renumber
everything after them.

### `raw-aux/` — the PowerShell 4104 file

| File | Records | Dialect |
| --- | --- | --- |
| `powershell-4104.jsonl` | 1 | PowerShell 4104 script block, JSONL |

It sits *beside* the pin folder rather than inside it, for the reason just given: adding a
3,860th event mid-stream would shift every later id.

The record is derived from the scenario rather than invented separately. `evt-00676` — the
`DEVBOX-07` PowerShell spawn — carries a base64 `-EncodedCommand`; decoding it as UTF-16LE
gives exactly the `ScriptBlockText` in this file. That is what a real estate with Script
Block Logging enabled would have recorded for the same intrusion.

`test/ingest/powershell-4104-lane.test.ts` holds both halves of the arrangement: the lane
parses, validates and yields a script-block entity, **and** `fixtures/raw/` still contains
exactly four files.

### The three pipeline-stage files

| File | Contents |
| --- | --- |
| `events.json` | 3,859 normalized events — 1,614 `zeek/conn`, 1,614 `sysmon/network_connect`, 480 `zeek/ssl`, 151 `sysmon/process_create` |
| `events_enriched.json` | the same events after stage-2 event enrichment |
| `candidates_enriched.json` | the 10 candidates above, fully scored, attributed and enriched |

`events.json` is **derived** from `events_enriched.json` by
[`scripts/derive-stage1-fixture.ts`](../scripts/derive-stage1-fixture.ts), which removes
exactly the `enrichment` key from each event and re-serializes canonically. Stage 1 is by
definition stage 2's input, so deriving it guarantees the two are one lineage rather than
two files that have to be kept in agreement by hand.

```sh
node --import tsx scripts/derive-stage1-fixture.ts          # write
node --import tsx scripts/derive-stage1-fixture.ts --check  # verify only
```

`test/conformance/pin-a-full-pipe.test.ts` asserts the derivation in both directions on
every test run: stripping stage 2 off the enriched fixture reproduces `events.json`, and
running athanor's stage 2 over `events.json` reproduces `events_enriched.json` byte for
byte.

## These files are a contract

`candidates_enriched.json` is an **expected output**, not a build artifact. Three
conformance pins assert byte-for-byte equality against it, entering the pipeline at three
different points:

| Pin | Path |
| --- | --- |
| **A** | `events.json` → the full pipeline |
| **B** | `events_enriched.json` → stages 3 onward |
| **C** | `raw/` → ingest → the full pipeline |

Pin C additionally asserts an intermediate: the events reconstructed from `raw/` must equal
`events.json` **before** the candidates are compared, so an ingest defect reports as a
divergent event id rather than as a candidate diff.

**If a pin fails, the code moved. Fix the code, not the fixture.** Regenerating a fixture
to make a test pass converts a caught regression into a silent one. If the output shape
genuinely needs to change, that is a deliberate change to the contract and gets explained
as one.

Hand-editing `raw/` has the same status. The four files are the rendered form of the same
event stream `events.json` holds, and they round-trip through ingest exactly.

## Ids are reconstructed, not carried

Raw logs have no event ids. Canon ids are `evt-%05d`, assigned by a global timestamp sort
across every dialect at once, so ingest reproduces the sequence rather than reading it:
merge every parsed dialect by **(timestamp in ms, dialect rank)**, then number the result.

```
zeek/conn 0  ·  sysmon/network_connect 1  ·  zeek/ssl 2  ·  sysmon/process_create 3
```

Only `zeek/conn` before `sysmon/network_connect` is grounded in the data — all 149
equal-timestamp groups in this dataset are exactly that pair, the network and endpoint
views of one connection. The other two ranks exist to give the rule a total order.

**Consequence, and it is inherent to the id model rather than a defect:** adding telemetry
to a folder changes evidence ids, and therefore changes every content-derived candidate id
downstream. A file inserted mid-stream shifts every later id by one.

## Field-map notes to read before you read the logs

- **`raw/conn.log` has no `id.orig_p`.** The normalized conn record carries no `src_port`,
  and inventing an ephemeral port would be fabrication. The parser accepts one when a real
  estate logs it.
- **`raw/sysmon-eid1.jsonl` carries a non-Sysmon `host.ip`.** Sysmon EID 1 has no host-IP
  column, but the normalized record carries `src_ip`, and the three `DEVBOX-07` events use
  a NetBIOS `Computer` value that would make it unrecoverable. `host.ip` is ECS shipper
  metadata — exactly what winlogbeat and Elastic Agent add — so the value travels without
  pretending to be a Sysmon field.
- **`raw/sysmon-eid3.jsonl` `Image` is a bare basename.** The normalized EID 3 contract has
  no `process_path`; ingest derives `process_name` from the basename and emits no path.
- **`-` is the unset token** (Zeek's convention, and Sysmon's for absent PE metadata).
  Ingest maps it back to `null` for the TLS contract's `string | null` columns and to an
  omitted field for Zeek's `service`. No value in this dataset is literally `-`, so the
  mapping is unambiguous here.
- **The `ssl.log` `uid` values carry through verbatim.** They do not overlap the `conn.log`
  uids, and that failed join is precisely what gives `TLS-001` its
  `confidence: "unavailable"`. It is not a bug to fix.
- **The scorer-facing ssl aliases** (`server_name`, `ja3_hash`, `ja3s_hash`, `cert_subject`,
  `cert_issuer`) are filled by the ssl **parser**, alongside the raw Zeek column names the
  log actually carries.

# `sample-estate/` — a second estate to practice on

Everything above is a **contract**: three pins hold it to the byte, which makes it the
wrong folder to experiment in. `sample-estate/` is the other kind of sample — a second
synthetic estate in the same four raw dialects that **nothing pins**. Point athanor at
it, lower a floor, narrow `distill_candidates`, and watch the numbers move.

```sh
athanor fixtures/sample-estate -o candidates.json --discards caput.json
```

**Nothing here was captured from a real network either.** The estate, its one host and
user, the implant and every process are invented. The benign traffic is addressed to the
public developer services a workstation really does talk to — that is what makes the
background legible as background — but no byte of it was observed anywhere.

## The scenario

1,294 events over eight hours on 2026-03-09, all from a single developer workstation:
`DEV-WS03` (10.42.10.45), one user, `CORP.LOCAL\jane.roberts`. The ordinary day is
GitHub, the npm registry, Docker Hub, Slack, VS Code and a great deal of `node.exe`.

`svchost-health.exe` is the implant. It beacons to 185.225.73.217 on 443 — 361 of the 422
connections — over TLS with a self-signed certificate and no SNI, and pushes ~86 MB out
to a consumer file-sharing endpoint. Five scorers, reading three dialects, with no shared
state, all land on it:

| Id | Score | Where it points |
| --- | --- | --- |
| `BCN-001` | 0.9031 | `svchost-health.exe` → 185.225.73.217 |
| `DT-001` | 0.9091 | the same binary's outbound volume → 31.216.144.106 |
| `TLS-001` | 0.8500 | the same connection again, as a certificate and SNI anomaly |
| `UPCA-001` | 0.9500 | `Code.exe` → `powershell.exe` — the editor is the parent |
| `PSI-001` | 0.9000 | that PowerShell's own `-EncodedCommand` line |

**And 26 candidates fall below the floors**, which is the better half of why this estate
is worth having. Twenty-five are `powershell_invocation_anomaly` at exactly 0.3: a
developer's `node.exe` opening shells all day. Run it with `--discards` and read one — a
floor is only ever auditable from the pile it dropped, and this pile is big enough to
have an opinion about.

The contrast with the pinned sample is the lesson: 3,859 events → 10 candidates and 3
discards there, 1,294 → 5 and 26 here. Same code, same defaults, a different estate.

## This folder is NOT conformance-pinned

There is no golden output for it and no pin measures it.
[`test/fixtures/sample-estate.test.ts`](../test/fixtures/sample-estate.test.ts) asserts
only that it ingests cleanly — 1,294 events from 4 files, no ordering ambiguity — and
that the defaults still distill 5 candidates and 26 discards from it. That is a
count-level canary, not a contract: it catches a change that quietly altered the
pipeline's answers on a dataset the goldens never see, and it costs nothing to move
deliberately.

Byte-level truth lives with `raw/` and `candidates_enriched.json`. This is the folder you
are allowed to break.
